# 账号

涉及登录、账号资料、头像、账号 HTTP API（oRPC）、云同步设置、站内反馈或管理员身份时查阅。存储层见 [Database](Database.md)。常量、限额、路径、环境变量读代码（`infrastructure/auth/`、`application/AccountService.ts`、`transport/routes/Account.ts`、`shared/Account.ts`、`shared/ApiContract.ts`、`config/Env.ts`）。

## 1. 身份与边界

- 账号以 **QQ 号**为身份锚点：登录邮箱只接受 QQ 邮箱，QQ 号由服务端建号钩子从邮箱派生，客户端不能自报。
- 登录方式：邮箱验证码（库内只存摘要，有尝试次数上限）与通行密钥（WebAuthn）。首次登录即注册。通行密钥只能由**已登录账号**添加，永远是验证码登录之后的加成，不能凭空造出账号。
- 通行密钥的 `rpID` 必须是**前端页面域名**：Ceremony 发生在页面源里，取后端域名会“注册成功、登录必败”。域名烧进凭据，已有密钥后再改等于全部失效，所以跨子域或换域名必须在第一位玩家添加密钥之前定好。
- 原生壳（WebView）也必须是该域名的页面源，并在该域名发布 `/.well-known/assetlinks.json`（包名 + 实际签名摘要）：WebView 只对与宿主应用关联的站点开放 WebAuthn，origin 不同域或关联文件缺失时系统验证器不会出现。壳内的配置与验证前提见 [Mobile/README.md](../../Mobile/README.md) §7.5。
- 每把密钥都要带名字入库：插件不替站点取名，注册时不传名字，列表里就只剩「未命名通行密钥」，两把密钥无法分辨。名字由前端按设备自动取，玩家随后在资料页改名；改名只改库里的 `name`，不动凭据本身。
- 账号昵称强制取自 QQ 昵称，注册后不可修改，与游戏内昵称互不捆绑。
- 游客游玩不受影响。账号系统随 `DATABASE_URL` 启用，未启用时账号相关前缀统一回 503 `ACCOUNT_DISABLED`，前端据此隐藏登录入口。账号接口失败（`ACCOUNT_DISABLED` 以外）按游客处理并记告警，**绝不挡住游玩**。
- 前端只展示中文错误文案：oRPC 错误取 `message`，Better Auth 的英文错误码在客户端映射成中文，其余退回兜底文案。

## 2. HTTP 面

- Better Auth 只开放白名单路径（`AUTH_HTTP_PATHS`）：验证码登录、取会话、登出与通行密钥的少数端点；其余（含它自带的发码、注册、改资料、admin 等）一律 404。新增对外端点要显式加入白名单。
- 发码走 oRPC：Better Auth 自带发码端点会把投递异常吞进后台日志，用户白等，因此不开放。投递失败返回 503 `MAIL_UNAVAILABLE`。
- 通行密钥端点只能由浏览器直连 Better Auth，**不经 oRPC 转发**：挑战值写在签名 Cookie 与库中，转发丢掉 Cookie 必然 `CHALLENGE_NOT_FOUND`。
- 验证码登录的前置钩子必须在**消耗验证码之前**校验邮箱、拒绝客户端自带头像、要求新号带昵称，避免用户白白作废验证码。
- 业务错误码到 HTTP 状态的映射只有一份（`statusOfAppError`），HTTP 全局错误钩子与 oRPC 共用。
- oRPC 契约的每个过程用 `op(说明, 鉴权层级)` 声明 `meta.description` 与 `meta.auth`（`public` / `session` / `admin`），不再另写文档注释；对外 OpenAPI 产物由导出脚本据此生成。`meta.auth` 必须与路由里实际套用的中间件一致，由 `RpcOpenapi` 测试逐一核对；新增过程漏写 `meta` 时生成器直接抛错。

## 3. 限流

- Better Auth 自带的按 IP 限流与 IP 记录关闭：它只认 socket peer 且会落库，经反向代理时全体客户端共享代理 peer，会误伤全站。
- 账号路由层自行限流：用 `resolveClientIp` 取边缘写入的真实客户端地址，与打点、Sentry 隧道同一口径（单客户端 / 回源 peer / 全局三层）。auth 与 RPC 共用同一份额度，超限回 429 `RATE_LIMITED` 并带 `Retry-After`。额度口径要容得下正常玩家（一次进房连着多个 RPC、后台列表轮询）。
- 发码有按邮箱冷却、按邮箱小时上限与全站上限；冷却秒数与前端倒计时共用常量。
- **头像代理是独立额度**：一页资料卡会同时拉几十张头像，共用一桶必然误伤正常玩家。但独立不等于放松——键是 `userId`，连续换号遍历等于按号枚举，所以同样超限回 429 并带退避头。
- 验证码暴力尝试由“每枚尝试次数上限 + 发码配额”共同约束。

## 4. 头像、隐私与 QQ 昵称

- QQ 号默认不公开，只有本人开启后资料卡才返回。QQ 头像源地址里带 QQ 号，**不得出现在任何他人可见的响应里**，浏览器只拿站内代理地址。登录弹窗展示自己刚输入的号的头像是例外。
- 头像代理的缓存头：版本参数等于当前摘要时长期 immutable，否则短缓存。头像字节只缓存在进程内存，不落库；回源失败保留旧头像，只记告警。
- 昵称回显接口不必发信就能拿到昵称，是个按号枚举的入口：必须按客户端地址限流，**绝不回答该号是否已注册**；已注册只回库内昵称、不为一个输入框去打上游，查不到回空、不挡发码。查询号未配置时该接口整体沉默——直接回空、连库都不查，否则「非空 / 空」的差别本身就是一份注册状态答案。
- 昵称来源是管理员自建的 NapCat（OneBot 11 HTTP），站点不持有 QQ 登录态。NapCat 地址与令牌成对配置，缺一即启动失败；两者都不配则昵称查询整体停用，**新号注册随之停用**（老号登录不受影响）。NapCat 只走内网直连，不经边缘与公网；这条约束靠部署侧把域名解析到内网 IP 实现，一旦解析回落到公网，请求会经边缘回源、被源站白名单 403，后台应报「拒绝访问」——报成「返回格式异常」说明错误分类退化，先查部署侧解析。
- 新号发码前必须在时限内取到昵称，取不到即拒绝发码；建号钩子再解析一次，仍取不到则拒绝建号。昵称经统一清洗函数处理（QQ 昵称常带不可见方向字符）。
- 昵称跟随：访问时按间隔后台刷新，查不到时保留旧值。批量刷新有单次上限、同一时刻只跑一轮，一次没查成即整批不动。掉线不做持久标记。
- 后台 QQ 状态检测不缓存（点“重新检测”必须反映真实状态）；批量刷新先写审计。

## 5. 游戏内身份

- WebSocket 握手带 Cookie 时解析会话，结果写入连接记录的 `account`。头像按 ID 读库，不用会话 Cookie 缓存。
- 账号系统故障或会话无效时以游客身份进入，**绝不拦截游戏握手**。
- 玩家接管座位（加入、重连、顶号）时取当前连接的账号。登录或退出后前端须重连 WebSocket 才会刷新身份（`refreshSocketIdentities`）。
- 房间快照只带 `userId` 与头像地址，不带账号昵称、QQ 号与身份徽章；资料卡与徽章由前端按 `userId` 查询。
- 前端 `PlayerRow` 收 `player.account`，资料按用户在同一访问内只取一次，失败不缓存。

## 6. 云同步设置

- 一行一个键，整体覆盖，不做字段级合并；偏好文档由前端自定，服务端不解释字段，有大小上限。
- 音乐账号按平台分键，内容含平台 cookie，**必须加密后落库**（附加数据绑定用户与键，密钥派生自服务端密钥）。密文挪行、篡改或密钥轮换一律视为云端无数据并记告警，用户重新登录音乐账号即覆盖。
- 只有本人能读写自己的设置；退出平台时删除云端副本。
- 前端只同步昵称、音量与房间设置记忆等偏好，不含房间恢复、访客 ID 等本机状态。冲突口径：偏好逐键合并、同键云端为准；音乐账号云端有则写回本地。读取云端失败时本次访问不同步。

## 7. 站内反馈

- 只有登录用户能提交，有频率与长度限制。落库后同步到 Sentry User Feedback，**只带账号 ID 与昵称，不带邮箱与 QQ 号**；Sentry 失败不影响站内反馈。
- 未读口径：最后回复晚于用户已读时刻。读取详情时标记已读，他人的反馈一律 404。管理员回复时 `open` 自动转 `processing`。

## 8. 管理员

- 管理员名单中的 QQ 号建号时即为 `admin`，启动时把已注册的同名单账号提升为 `admin`。**只提升不降级**，降级在管理后台完成。
- 管理接口挂在 oRPC `admin.*`。每次调用按 ID 读库校验 `role=admin` 且未封禁，会话读取一律跳过 Cookie 缓存，降级、封禁与强制下线立即生效。
- 不能对自己封禁或改角色，不能封禁管理员（先降级）；被封用户须先解封才能提为管理员。封禁同时删除其全部会话，封禁中的账号发码直接 403 且不消耗发信额度。
- **每个写操作先写审计再执行**；审计写入失败则操作不做。审计不记 IP（理由同限流：边缘之后拿不到可信 IP 且不应落库）。
- 身份徽章（开发者 / 贡献者 / 内测 / 赞助）只由管理员人工授予、撤销，**没有按行为自动解锁的成就**；同一账号同类徽章只有一枚，重复授予保持一枚。授予关系落 `user_badge`，目录由启动时按 `shared/Badges.ts` 幂等补齐。徽章随 `account.me` 与 `account.publicProfile` 返回，不进房间快照。
- 实时房间的关闭与移人由各游戏实现统一的 `AdminRoomControl`，后台不直接改房间状态，复用各游戏的关房通知与踢人结算口径；房间视图不含会话令牌与对局秘密。CEE 只管增强房。
- 后台代查 Sentry 的令牌只在服务端，返回与日志都不得含令牌；各查询独立容错并缓存。

### 访问统计

- 前端每进入一个新板块上报一次，同板块内换房不重复；账号系统未启用时静默忽略。
- 服务端进程内聚合、定时刷写，写库失败丢弃该窗口。访客 ID 落库前与“派生密钥 + 北京时间当天”做 HMAC：**跨天不可关联、库内还原不出原 ID**，不记录 IP。
- 页面只按板块统计，房号折叠、未知路径归 `other`，统计表不得按房号膨胀。窗口内新访客有上限保护进程内存。

## 9. 配置约束

变量名与取值以 `config/Env.ts` 和 `Server/.env.example` 为准。约束：

- 配置了数据库连接就必须配置足够强的认证签名密钥（变量名读 `.env.example`）。
- 生产必须配置 SMTP；开发用的“验证码打印到终端”开关生产启用即拒绝启动。
- 通行密钥域名必须是裸域名（含协议、端口、路径即拒绝启动）。
- 会话 Cookie 生产强制 `Secure`；来源判定与 WebSocket 共用同一个来源校验函数。

## 10. 验收要点

验证范围见 [Testing](../../Agents/Testing.md)。使用内存适配器与假上游，不连真实数据库、QQ 头像源与 NapCat；真实数据库、SMTP、NapCat 只能人工验收，结束后删除测试账号。必须覆盖：

- 账号：发码与登录、昵称强制取自 QQ、端点白名单、通行密钥域名、限流（auth 与 RPC 共额度）、投递失败、管理员引导、隐私与头像缓存、昵称回显不泄露注册状态。
- 设置与反馈：整体覆盖、加密与越权、限流与未读口径。
- 管理：权限分层、降级即时生效、封禁（踢线、拦发码、到期恢复）、自我与管理员保护、审计先行（含写入失败）、徽章授予/撤销与当前用户查询。
- 统计：路径折叠、访客摘要跨天不可关联、写库失败丢弃、Sentry 客户端令牌不外泄。
- 前端：接口错误文案、云同步范围与合并、登录弹窗昵称冻结与就地报错、通行密钥入口与失败提示、密钥自动命名与就地改名、资料卡缓存与重试。
