# 猜番曲目匹配与出题

涉及手动或自动出题、曲目类型、歌曲匹配门禁、专辑兜底、同名防错与出题性能预算时查阅。Bangumi 请求边界见 [BangumiApi](BangumiApi.md)，数据集口径见 [BangumiDataset](BangumiDataset.md)，网易云检索与解灰见 [NeteaseMusicApi](NeteaseMusicApi.md)。门禁函数、打分权重、阈值、预算常量、正则读代码（`Server/src/application/` 下的曲目解析、`Server/src/shared/SonGuessr.ts`、`infrastructure/LocalBangumiProvider.ts`），本文只记**为什么这样设计**与不能破坏的不变量。

## 1. 出题总则

- 手动出题先搜索条目，再从关联音乐条目与 infobox 提取曲目；提取时通过正则排除制作人员 Staff 字段，避免把人名当歌名；曲名支持多书名号提取与斜杠拆分。
- 猜番模式下玩家猜的是番剧名，曲目名只用于结算展示。因此“出一首确实属于该番的歌”远好于整条出不了题，兜底路径可以放宽“哪首歌”。
- 自动出题的候选条目按顺序尝试并避让近期番剧；歌曲热度不达标时优先继续同一作品的其它曲目，该作品所有曲目都不可用才切换作品；全部失败返回 `BANGUMI_NO_MUSIC`。
- 没有曲目信息、没有可播放歌曲或会员权限不足时拒绝提交，并保持当前出题阶段不变。
- 曲目类型只在结算摘要公开：出题阶段的房间快照不含歌曲与曲目信息。校验曲目类型的测试与功能必须走“出题 → 结算”路径，不能从出题快照读取。结算摘要最多公开少量作品标签，不公开元标签。

## 2. 检索与匹配门禁

- **限定检索**：没有明确歌手时，检索词附加番剧原名与中文译名以消除重名干扰；有歌手时仍追加番剧名与纯曲名的宽检索，避免两个站点歌手写法差异导致原版漏召回。**过长的歌手名不得拼进检索词**（Bangumi 的歌手字段常是整串声优列表，会毁掉检索）。
- **曲名门禁**拒绝与目标曲名不符的异形结果，三条不变量：
  - 多曲并列先拆段，任一段完全一致即命中；**拆段只认真正的曲目列表分隔符**，不认可能出现在作品名内部的标点（否则会拆出无关的同名曲过门禁）。
  - 候选名更长（带番剧名、版本后缀）保持宽松。
  - 候选名更短必须收紧（长度与占比双门槛），否则毫无关系的短名会被放进来。
  - 门禁与准入打分用的相似度**必须共用同一门槛**，否则短词会靠“被包含 + 番剧上下文”凑够证据。
- **曲名命中或专辑名与曲目名完全一致**是两条独立的召回通道。后者是必需的：Bangumi 会把整张原声带挂成一条关联曲目，里面真正的曲目只有专辑名能命中。
- **准入证据与排序分解耦**：能否进入验证队列由独立的证据判断决定，不复用排序分数。
  - 曲名完全一致 → 准入，**不看歌手**（翻唱照抄曲名，歌手写法差异又常让交集为空，用歌手否掉会让原版没有被验证的机会）。
  - 专辑名与原曲目名一致 → 准入。
  - 曲名只部分命中 → 必须另有独立锚点（歌手交集，或专辑名含番剧名且带发行上下文）。
  - **“出现在带番剧名的检索结果里”不得单独充当准入证据**（模糊检索会召回无关同名曲，对短名几乎恒真）；它只保留在排序加分里。
  - **非原唱标记的降权不得参与准入**：降权属排序，算进准入会让唯一候选是翻唱的曲目退化成无歌可出。
- **原版优先排序**：通过准入的候选先打分再依次验证可播放性。评分维度与权重设计的意图：曲名相似度、专辑名与曲目名一致（原唱通常发行在同名专辑，同名翻唱挂在自建合辑下）、番剧上下文命中（区分原版与别人家的同名原创，权重刻意低于歌手交集这一更硬的证据）、歌手交集加分/无交集减分（Bangumi 未记录歌手时不参与）、非原唱标记降权（翻唱、伴奏/现场、器乐改编）。标记词**只在 Bangumi 曲目自身没有该标记时生效**，否则题面本身是 Cover/Arrange 的曲目会被整体降权。网易云会把翻唱与器乐改编混排在原版之前，排序保证原版存在时不被抢占；只能召回翻唱时仍正常出题。
- **手动选曲列表一个关联曲目只出一个代表候选**（原版优先分最高者），否则同一首歌的多个版本会刷满列表并混入翻唱；专辑兜底路径返回的是整张专辑的不同曲目，全部保留；跨条目去重挡下的候选直接跳过，不顺延到次名版本。自动出题不受此限。

## 3. 版本与同名防错

- **翻唱必须让位**：网易云歌曲详情里的原唱/翻唱标记是**唯一可靠**的版本信号（翻唱可以把曲名专辑名照抄成一字不差）。它只在详情里返回，所以让位只能发生在验证阶段。
  - 翻唱候选记为兜底，**不占用详情验证次数**（否则成批排在前的翻唱会吃光名额）；兜底优先级：近期重复的正确歌 > 年份错配 > 翻唱。
  - **用翻唱自带的原曲 ID 回指原版**：原版常常压根没进候选池，把该 ID 插到队首比补检索词更直接；用集合去重防止翻唱互相指向反复插队。
- **同名不同曲用发行年兜底**：文本维度对曲名专辑名都撞车的同名歌无能为力，所以验证阶段按“候选发行年与番剧首播年的差距”判错配。不变量：
  - 发行年只在详情里返回，只能在验证阶段生效；
  - 错配候选**不占用验证次数**（同名新歌常成批排前面）；
  - 容差刻意宽松，既挡跨代错配，又保留同一录音的合法再版/纪念盘；
  - 年份未知放行；全部错配才用年份兜底，优先级低于近期重复的正确歌。
- **只有常规检索路径允许翻唱与年份兜底**：专辑与番剧级兜底已经放宽了“哪首歌”，再放宽“是不是原版/同一年代”会叠出错配（同名新曲顶掉老番原曲）。
- **近期防重**：房间维护近期番剧与近期歌曲的滑动窗口，自动出题优先避让。歌曲窗口长度按**过滤会员曲后的整池**自适应；排除近期曲目与写入窗口必须用**同一个数值**；窗口**不得**由“扣除近期后的剩余”反推（池子被扣小时窗口跟着缩，等于每回合自动放宽去重）。只有自动选曲知道池规模，手动出题与猜番用默认窗口。
- **所有通过筛选的曲目必须等概率**：先对通过类型筛选的曲目洗牌再截断、遍历，**严禁按数据源顺序取首个可播放曲目**（本地数据集与联网 API 都天然偏向片头曲）。洗牌后截断，使被预算截掉的曲目同样等概率命中。

## 4. 专辑型条目与兜底

Bangumi 把大量资源挂成整张专辑条目，条目名就是专辑名，拿它当歌名检索单曲必然一无所获。

- **触发**：常规检索候选池为空、且条目类型不是非音乐类，才走“搜专辑 → 取专辑曲目”。类型用**黑名单**（广播剧/电台/朗读）而不是白名单：按白名单会让片头/片尾条目里塞着的整张角色歌 CD 永远零候选。**不要按条目名像不像单曲推断条目形态**。
- **检索词必须覆盖番剧名，逐级放宽**：条目名 → 剥掉番剧包裹后的余部 → 番剧名 + 类型关键词 → 番剧原名 → 番剧中文名。只用条目名会全军覆没，原名常是英文，须单列一级。匿名态的多重匹配接口返回空，不可用。
- **专辑名用相似度分，不是“必须对得上”**：两站点的命名必然有出入，只用全等/包含会把真专辑判死；序号加分是为了不抽到系列里的隔壁那张；判据不能只看长度比例。
- **专辑名恰好等于番剧名时直接判 0**：条目名只会是“番剧名 + 前后缀”，与裸番剧名的包含是结构性必然、证据强度为零，否则用户自建的同名盘会压过官方特典 CD。例外：专辑名带发行上下文、专辑歌手与条目歌手有交集、或条目名与专辑名全等。
- **歌手对不上时，子串命中的专辑必须自带番剧归属**：只放行专辑名与条目名归一化后全等，或专辑名含番剧名且带发行上下文。
- **曲目读响应顶层的曲目列表**：专辑详情里嵌套的曲目在同名/单曲专辑上是空数组，用空值合并写法不会回退，整条专辑路径会静默失效；有回归用例钉死读取顺序。
- **同名专辑优先选艺术家对得上的那张**，都对不上退回第一张交给验证阶段筛。
- **专辑取曲原版优先**：版本分轨（Remix/TV Size/Game Size）**只降级不剔除**，原版组洗牌后排前；伴奏/纯音乐/现场/翻唱分轨在专辑路径直接剔除。
- **最后一道兜底是番剧级检索**：用番剧名搜单曲，只保留能证明属于该番的候选（专辑名含番剧名且带发行上下文，或歌名与该番任一 Bangumi 曲目标题一致）。代价是可能出到该番的其它曲目，可接受。专辑名含番剧名还不够，必须另有发行上下文（否则泛用名撞车会让同名新歌顶掉老番主题歌）。
- 兜底路径拿到的歌不属于本条目，曲目类型必须按歌曲自身文本推，不能沿用条目分类（否则会显示成“Radio”）。
- **非歌音轨必须在所有路径否决**：专辑名等于条目名即放行的门禁，会让整张特典 CD 里排最前的对白轨、广播轨、电台谈话、伴奏、纯编号轨混进来。这类否决发生在验证阶段、覆盖全部路径、**不占验证次数**；它与“选哪首”的粗筛分工不同：现场/不插电/器乐改编只是版本不同，仍有人声，全路径只降权。正则只认节目分轨形态，**不碰叫《ラジオ》《ドラマチック》的正常曲名**。
- **多检索词必须并发，验证必须串行**：同一条目的检索词无依赖，必须并行（自动出题是实时链路，串行会把等待按词数放大）；候选验证逐首短路（见 §6）。守卫测试用“闸门探针”：断言最早返回的请求落地时所有检索词都已发出。

## 5. 曲目过滤与类型

- **曲目池必须先剔除版权署名伪条目**（版权方、制作委员会、动画师署名等）。它们在本地数据集里 `music_id` 为负数，却被归到片头曲类目并排在所有真实曲目之前。两道防线缺一不可：本地查询带 `music_id > 0`（结构判定）；文本判定由共享函数 `isBangumiCreditsEntry` 识别版权/录音权标记与不带歌曲语义词的“製作委員会”署名，数据提供方与曲名门禁共用这一个真相源。
- **判定规则只准收紧到无歧义标记**：不要把 `♡ ❤ ※ ☆ オール 单曲 精选` 这类正常曲名常用元素纳入规则。新增规则必须用真实数据集全量回归，断言“正 id 误杀 = 0”，并补反向用例。
- **关联类型码只在服务端映射一次**，以 `LocalBangumiProvider` 的映射表为唯一真相源；映射错位会让“按曲目类型筛选”选出完全错误的曲目，核对必须用真实数据集复现。修改映射必须同时改构建脚本与对应测试的关系码断言。
- **主题歌是个大杂烩桶**（原声带、特典 CD、广播剧 CD 都挂在下面），必须再用条目名细化：具体类型的关系码直接采信，主题歌与未映射码走共享文本细化函数，推不出来才保留主题歌。数据集里构建期写死的粗分类列不再被读取（读它会形成双真相源）；类型在读取时按“关系码 + 条目名”现算。关键词必须覆盖带空格的写法。
- **曲目类型校准以歌曲自身标注为准**，判定统一走共享函数，服务端（出题、手动选曲）与客户端结算徽章**共用同一真相源，严禁各写一套正则**（后果：同一首歌服务端算成原声带、客户端显示成主题曲）。两层：无歧义的显式标注（片头/片尾/插入歌）优先级最高，因为 Bangumi 的关联分类常更粗；发行形态关键词（原声带、特典、角色歌、广播剧等）**只在条目类型是主题歌桶时生效**，其余具体分类原样保留。

## 6. 出题性能预算

自动出题要连续回源多个外部接口，冷缓存下必须按**真实成本**设预算，否则一次出题会退化成数百个上游请求。预算常量（搜索次数、详情验证数、单曲目验证版本数、单次检索取回数、番剧候选数）读代码。

1. **搜索与详情验证分开计预算**：一次搜索是一个上游请求；一次验证要拉取完整歌曲详情（详情 + 百科 + 热度 + 歌词 + 音频，约五六个请求），成本是搜索的数倍，**严禁与搜索共用同一个计数**。
2. **候选详情逐首短路**：按原版优先顺序逐个验证，首个可播放即停，**严禁为同一曲目的多个候选并行拉取完整详情**（并行会把被丢弃候选的成本也付一遍）。
3. **不按会员状态预剔除候选**：会员专享曲由解灰链路取回完整音频，账号是不是会员不参与出题判定，可用性以“实际拿到的音频”为准。解灰拿不到整曲时抛 `SONG_UNAVAILABLE`，候选级调用方当作“这个候选不能用”换下一个，限流与接口整体不可用必须原样抛出。热度门槛无法由检索结果判定，用一次廉价的红心数查询先判掉，避免为必被否决的候选拉歌词与音频。
4. **长任务不设客户端请求超时**：开局与下一轮的耗时由上游决定，客户端以无超时发送，并在等待期间周期性同步房间状态。严禁用默认短超时（那只会制造“后端还在选曲、前端已提示失败”的假失败）。

## 7. 抽样探针与失败归因

- 探针放在不进仓库的本地目录（见根 `AGENTS.md`「本地笔记」）。它直接 import 生产的门禁/打分/检索词函数，只在本地复刻**编排顺序**，规则绝不复制一份。
- **测试集必须与开发集“作品级”零重叠**，否则等于拿训练集做推理；先冻结样本再跑，保证多轮之间比的是同一批曲目；分层抽样热门略多于冷门，同一作品每档最多一条。
- **网易云是累积型软限流**：配额吃紧时检索**返回空结果而不是报错**，批量探针会把“被限流”误记成“网易云没有这首歌”。探针并发 1、条间留间隔、空结果退避重试；判“真没有”之前先单条复测；命中限流就换出口（新 Provider 实例 = 新伪装 IP + 冷却清零）；每条样本记录限流次数，汇总时把“真无候选”与“被限流”分开归因。不要在同一台机器上并发做别的回源，会共用限流额度互相污染。
- **无候选的归因三分法**：① 专辑检索一张都没搜到 → 网易云确实没有，无解；② 搜到专辑但名称分全为 0 → 命名差异太大，检查专辑名相似度的特征词；③ 有候选却被挡下 → 回查曲名门禁与准入证据是否过严。

## 8. 数据集补列与发布下载

补列走增量补丁只更新一列，不重跑完整构建（会覆盖线上角色标签）。从 release 下载数据包时必须用精确文件名，通配符会命中该 release 的全部历史 asset。
