# CEE 多人玩法与互通契约（服务端）

修改增强房玩法、原版互通、权限、会话或搜索时使用本文。界面与客户端行为见 [Client/docs/CEE](../../Client/docs/CEE.md)。阶段名、协议字段、计分数值、限额、超时、环境变量名读代码（`Server/src/shared/CEE*.ts`、`domain/CEE*`、`application/CEE*`、`transport/` 下 CEE 路由）；数据口径另查 [BangumiDataset](BangumiDataset.md)。

原版行为依据相邻仓库 `anime-character-guessr`（`server/utils/socket.js`、`gameplay.js`、`client/src/utils/bangumi.js`）；增强版规则以本文与代码为准，不恢复旧页面或服务。原版联调前必须核对相邻仓库分支、远端提交与目标部署版本，完成情况以测试和目标环境证据为准，不凭文档断言。

## 1. 产品边界

- 房间来源分增强房与原版房。增强房由本服务权威执行；原版房建在配置的原版服务器，每位增强版玩家通过独立上游连接参加。原版适配器不另跑本地比赛。
- 两类房的增强版角色检索与判定资料都来自本地 SQLite。原版客户端资料版本可能不同，允许反馈差异；兼容房的最终状态、计时、积分服从远端。上游当局答案快照必须保留，不擅自换成本地答案。
- 三款小游戏使用公共默认头像，不做角色头像选择、抽卡、兑换或 QQ 登录。
- 增强版没有玩家短留言，由聊天替代。兼容房的聊天只在增强版玩家之间互通，不把原版短留言伪装成聊天，也不改原版客户端的留言。
- 上游地址及 AES 配置只在服务端环境变量；绝不写入前端构建或日志。

### 统一房号

- 大厅、路由与会话只认一个房号，增强房与原版房共用号段，互不占号，唯一持有者是 `CEERoomDirectory`。增强房房号即自身 id；原版客户端建的房由服务端分配别名（按上游 id 散列取初值、线性探测避让，使刷新与重启后同批房间尽量得到同一别名）。**上游真实房号不下发给客户端**；服务端内部的上游连接标记同样不下发。
- 房号的校验与归一只有一份，即 `domain/Rules.ensureRoomId`，三款游戏的服务入口都调它；服务内不得另抄一份校验或自写拒绝文案，否则同一个非法房号在不同游戏里报出两样话。唯一例外是 `CEERoomDirectory.claimOriginal`：它在原版服务器占号，上游只认四位数字，因此必须比共享守卫更严，测试房号在这里同样被拒。
- 别名只在一次成功的上游列表里该房已消失、且没有本地会话（含建房确认途中）时才释放；上游暂时不可达不影响现有别名。入房时房号未命中会回源刷新一次（与大厅共用节流），仍未命中回 `ROOM_NOT_FOUND`。
- 原版列表不提供旁观人数，其值为 `null`，不伪造为 0。
- 私密语义：增强房私密即有密码；切到私密必须给新密码或已有密码，留空保留原密码，转公开清除密码。缺密码 `PASSWORD_REQUIRED`，错密码 `PASSWORD_INCORRECT`。密码尝试限流**在校验之前计数**，超限后正确密码同样被拒；除单连接限额外必须有按房间合计的限额，否则多开连接就能线性放大爆破速度。原版没有密码机制，其“私密”只控制是否出现在大厅，非公开原版房凭别名链接仍可进入。

## 2. 反作弊房（BakaAntiCheat）

通道证明本身见 [ClientChannel](ClientChannel.md)，本文只记房间侧口径。

- 该设置只在增强房出现，**只在建房那一刻决定**。进房后的设置载荷里这一位一律由服务端按房内现值覆盖，而不是报错：预设、配置导入、“沿用上次设置”都可能带进不同的值，拒绝整份保存会让房主改不了别的东西；中途开关则会让同一间房的人按不同口径准入。不开启的房间与过去完全一致，任何检测与门槛都不作用于网页玩家。
- 建房连接自己先要达标，否则房开不出来：无通道证明、版本过低、未登录各有独立错误码。客户端据此只对达标的建房者呈现这个开关。
- 进房准入三条硬条件：连接带服务端验过的通道证明、全员已登录、客户端版本不低于最低版本（普通房不拦版本）。旁观改为房主批准制，待批准队列有上限、超时自动拒绝。**断线重连走同一道准入，旧 `sessionToken` 不是例外。**
- 行为特征只用服务端可观测数据（猜测间隔及其变异、是否先搜索再猜、首猜即中、伪造检索）。规则打分，不做机器学习：样本不够，且无法向被复核的人解释。采集覆盖全部增强房对局（普通房数据只作语料，不判定、不对外呈现）。
- **代码路径里不存在任何自动封禁**：判定结果只进人工复核队列，代码只会写 `open`；处置只有后台一条人写路径（改为放行或已处置），先写审计再落库（见 [Account](Account.md)），后台不提供封禁、扣分或任何对局侧动作。对局写入与后台读取必须用同一个队列对象，避免两份口径。概览页的待复核计数只是入口提示，处置只在复核标签里做。
- 跨局视角只吃队列里已有条目的 id，窗口与条数上限在服务端，不接受前端传窗口，也不提供按昵称拉人的入口。身份口径：登录认 `userId`；游客只与同样没有 `userId` 的同昵称条目并列，不把昵称撞上登录账号的游客并进该账号。聚合纯读时计算：不落库、不加减分、不写审计，读失败不影响处置。
- 房间内只对所有人披露反作弊是否开启，以及本局是否已记录；都不点名、不指控。可疑度、特征与复核条目一律不进协议，只在服务端。

## 3. 玩法与状态

- 局号与同步轮号是不同字段。开局冻结设置；猜测只提交角色 ID，**不接受客户端判中结果**。
- 出题方式是设置项（随机/手动），两种来源都适用。手动出题进入独立选出题人阶段，只在该阶段接受选人指令，房主可取消退回；候选名单只由服务端下发给房主、客户端只消费。候选名单逐人重算开销为 O(n²)，私有状态又按连接生成，所以只为房主、只在手动出题的等待与选人阶段计算。
- 原版协议没有出题方式与选人阶段：出题方式只记在本服务端同房的全部会话上，不发上游；收到上游设置时沿用本地取值；选人阶段只在房主会话本地，上游推进阶段即清除。旧设置文件缺该字段时按随机补齐。
- 增强房至少两名在线参与者才能开局，只有测试房允许房主一人试玩；最后一人离开时先解绑再关房，离开者不收到关闭通知，与另外两款游戏一致。
- 房主没有准备态：两种来源都忽略房主的准备指令，开局只看其他参与者；转让房主后新房主视同已准备、卸任者回到未准备。
- 出题人与其队伍本局观战；中途新成员本局观战；已结束玩家只能观看、不能重复提交。
- 计分口径（数值读代码）：普通模式首位猜中结算；同步等当轮参与者全部完成才判定；血战继续到全部参与者结束。同步血战同轮答对并列，基础分在同步轮开始时冻结；同步胜者各按自己的首猜、本命与快速猜中奖励结算，不共享首位胜者奖励；非同步血战按消息顺序。**原版须对齐同一口径。**
- 血战出题奖励的分母冻结为开局实际猜题人数，排除出题人及其观战队友；猜题者之后断线、清理或离开不缩小分母，不得按结算时在线人数重算。
- 队伍共用尝试记录、次数与行动计时；超时按当时在线且可行动的队员数扣次数。胜者、贡献者与奖励用明确记录，**不从共享表情串反推玩家身份**。
- BP 规则：保留本人重复、同步同轮及正确答案例外；被拒绝的猜测不扣次、不登记标签；本人重复豁免不能扩大到同队成员。作品分从全局有序的猜测序列比较队员首次作品命中位置，不比较个人数组索引、姓名或同毫秒时间戳；先选队内最早命中者，再排除本人实际猜中角色的情况，队友最终猜中不能抹掉原贡献者的作品分。
- 标签发现与有效猜测原子提交，私有视图裁剪隐藏标签。原版服务支持时通过猜测载荷同步登记并以确认字段回执；不支持的实现只能退回独立标签事件，最后同步提交者的标签可能延后一轮。
- 默认多人设置与预设基础值不同，预设不能替代多人默认值；不限行动计时仍受房间闲置与阻塞阶段超时约束。

## 4. 数据与隐私

- 只读基础库与可写补全库组成统一查询结果；API 补全的头像 URL 与有效角色资料持久化，周更不覆盖补全库。**禁止把网络查询作为 SQLite 角色检索失败后的隐式回退。**
- 目录成员先同步入库，对局只用已落库成员；缺失条目给出明确数量。登场作品和标签池按房间设置运行时推导。
- 原版登记游戏的额外作品关系单独参与作品命中，不改变可见作品数量、评分及年份。外部标签使用服务端 SQLite 原始资料，不透传上游 HTML，不参与普通标签 BP；答案的完整外部标签继续受私有状态边界约束。
- 答案、设置和已使用角色视图在局内冻结；后台资料更新不得改变已给出的线索。
- 自动文本提示服务端生成一次；图片提示由服务端生成当前允许的模糊版本，未解锁时**不得发送原图、原图 URL 或可猜出的资源路径**。提示请求必须鉴权。阈值为零表示关闭，被隐藏标签同时移除原文与命中标志。
- 数值比较符号表示“猜测值减答案值”；未知评分和年份显示“未知”，不得暴露内部哨兵值。
- 公开快照只含公开房态；本人/队伍猜测、观众/出题人答案进入私有状态。兼容适配同样按连接视角裁剪，不能合并所有上游玩家的私有事件。
- **私有态不可为省字节合并成房间共享帧**：猜测的标签遮蔽按成员逐个判定，同一条猜测在不同成员眼里内容不同，共享帧会泄露未解锁标签。编码本身不是性能瓶颈，真正的成本在带宽和每帧命令数；要压容量，先压每帧命令数与房间数，且差分瘦身需要客户端发版才能收到，必须有实测依据再动。
- 原版客户端可解密答案是其协议局限，兼容房不宣称全房答案保密。

### 兼容房的局代数

- 兼容房由房间统一维护递增的对局代数，不能凭答案载荷哈希充当局号。同载荷在结束后再次开局也必须重建资料与自动提示缓存；多条上游连接只绑定同一代数，旧连接不得回退共享缓存。猜测、图片、附加标签及确认响应在异步返回后复核代数。
- 仅当前代数的结束事件关闭共享局；已知旧载荷的迟到开局事件不回退房间，指纹用有界缓存登记。上游不提供局 ID：未观察到结束边界且载荷完全相同的开局事件只能按同局重发处理，不能声称协议可以消除这种不可判别情况。
- 同房同局共享本地角色查询与附加标签资料，连续下一局重新读取；后来者进房即沿用共享房间已知代数。
- 旧原版答案仅在关联登记游戏时从 SQLite 补充附加标签和缺失作品名称，禁止覆盖上游答案数值、作品编号或可见作品统计；本地角色不存在表示无附加标签，数据库故障须报错。异步猜测跨过上游超时或同步换轮后必须拒绝旧动作。

## 5. 协议、解析与会话

- 统一入口 `/api/ws` 上的 `cee.*` 命令使用平台信封、TypeBox 严格边界、会话幂等与 RFC 6902 状态同步；旧 `/api/cee/ws` 仅为已发布客户端保留别名。领域、数据访问、原版适配和视图各自独立。
- **可选字段必须同时接纳“缺席”与显式 `null`**：前端把“尚未加入房间”表示为 `null` 并原样序列化，只写 `Optional` 会让合法请求在解析阶段被判 `INVALID_MESSAGE`（判定特征：400、微秒级耗时、日志仍是未解析的原始记录）。放开 `null` 不得放松任何取值约束。
- **解析失败必须保留信封身份，错误包 `id` 不得退化成占位值**：客户端按 id 匹配待决请求，匹配不到就静默丢弃，而进房类命令永不超时，页面只表现为一直卡住。网关须从校验失败的原始载荷里抢救 `id`/`type`（仅供错误回包与日志，不参与业务），并把裁剪后的载荷形态写进告警日志。
- **可恢复状态不得交给 schema 拒绝**：恢复会话的凭据为空或缺席属于“会话失效”而不是“消息非法”，由业务层回可归因的错误码。
- 进房与建房命令不带来源字段，只有建房声明要建在哪个服务器。
- **进入房间期间客户端不得抢跑状态同步**：服务端在返回进房结果之前就会发布新状态，快照事件先于 ACK 到达；此时抢发同步请求会被原版会话校验判无效，进而清掉刚建立的会话。客户端应把请求压成欠账，待 ACK 写回凭据后再补发（补发前先取走欠账标志）。
- 客户端会话凭据只按统一房号存储；来源与上游配置由服务端会话表判定，凭据对不上时回会话不存在/过期，客户端据此删除。确认加入后授予聊天身份，被踢/退房即时撤销。上游无法确认同号房是否重建时清除旧聊天，**禁止无限重试 join 导致意外建房**。
- 来源切换、会话恢复和主动请求同步都重置公开与私有状态的差量基线，首次发送完整状态。重连宽限内保留的上游会话计入玩家数，但没有下游连接时不得计入在线人数。
- 原版房列表返回含非公开房的完整列表：同时用于入房前存在性检查与别名分配，大厅只展示其中的公开房。
- 原版房名的状态确认按上游的截断规则，不能用更短的本地长度等待永远不会出现的确认。玩家身份比对要宽容：上游编号可能是数字、用户名可能带首尾空白，必须显式归一化，否则加入确认谓词永不命中、只能等到超时失败。
- 出题、续局、目录导入及图片处理等耗时命令依赖服务端受控截止时间，客户端不另设短超时报假失败。

## 6. 生命周期与并发

- 房间定时（房主重连、空房宽限、离线清理、闲置清理）由服务端驱动，断线不能导致同步永久卡住。唯一猜题人暂时离线不能直接结算；保留未结束席位供刷新恢复，离线清理、明确退出或放弃才结束该席位。
- 异步出题任务使用独立操作标识，截止时间不能兼作身份。猜测查询回来须复核局、同步轮和次数；同角色并发返回时复用首次接受的冻结资料。入房密码校验回来须确认连接仍登记。
- 原版随机开局与手动答案准备各持独立操作标识，冻结设置及原连接、房间代数、共享局、阶段、房主和出题人。每次角色或图片查询 `await` 后、发出上游事务前，复核该操作仍归当前连接且仍有对应权限与准备条件；命令串行队列不串行上游广播，也不能替代归属复核。断连、连接替换、离房、房主/出题权变更、取消出题、设置变更或新局撤销旧准备，权限随后恢复也不能复活旧任务；离房即时撤销，不排队。失败只回滚仍由该任务拥有的准备阶段，不能覆盖上游新局或新出题人；已发出的事务仍服从上游确认。

## 7. 搜索索引

- 角色和作品搜索由服务端 Worker 通过 `meilisearch` SDK 访问内部 Meilisearch，客户端仍经 CEE WebSocket 请求。SQLite 只保存详情和关系，不是搜索排序器；**Meilisearch 返回的命中顺序必须原样用于详情回填。** 实例地址与密钥是部署配置，不进文档。
- 排序规则与 Bangumi 官方搜索一致，先文本相关性规则，再按各自业务字段；搜索字段只有名称与别名，其它字段只作过滤或排序。规则以索引设置代码为准。
- Worker 初始化校验服务健康、创建/校正索引字段设置，并在文档数不一致时从本地 SQLite 分批重建。CEE 与猜歌共用同一实例。未配置密钥的本地/测试夹具保持显式本地模式；生产必须提供可用实例，**不能在运行期静默切换到另一套排序逻辑**。
- 作品按编号摘要查询只读本地 SQLite，有数量上限，不联网、不走搜索索引。
