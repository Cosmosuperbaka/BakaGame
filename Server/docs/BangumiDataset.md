# Bangumi 数据集与角色资料

涉及 SQLite 数据集构建、作品裁剪、角色标签、声优、登场作品与 CEE 运行时资料时查阅。图片回填与请求边界见 [BangumiApi](BangumiApi.md)，曲目提取与匹配见 [BangumiSongMatch](BangumiSongMatch.md)。表结构、列、常量、数量上限读代码（`Server/src/infrastructure/CEECharacter*.ts`、`LocalBangumiProvider.ts`、构建脚本 `tools/build_bangumi_db.py`）。

## 1. 数据集构建

- 数据集由构建脚本从 Bangumi Archive dump 生成，**本地一次性构建**，构建工具目录不进 Git。CI 不构建也不发布数据集；基线由运维上传，之后由后端自行更新（角色标签走增量 diff，作品标签与封面地址走 API 刷新，新条目按首播窗口发现）。
- **角色关系、作品与声优的运行时判定仅使用这些本地数据**；普通角色查询不得在缺失时回源补查。角色头像及同次 API 返回的基础资料、用户明确导入的目录成员使用独立的补全层（见 §7）。
- dump 有两个字段不可直接使用：作品 `tags` 被截断、`images` 整个不存在。构建产物必须用刷新脚本全量刷新一次（作品标签 + 封面地址）。
- **单库**：猜歌与 CEE 共用同一个数据集文件，作品只存一份，不得分库（分两处会更新不一致）。
- **作品裁剪口径**：没有角色关联、也没有关联音乐的作品一律不入库。因此作品表里**没有“数据缺失”这回事**：查不到就是本项目不需要，不是构建漏了。不得引入运行时零读取的音乐冗余表。
- 构建的发布顺序不能改：连接必须在替换文件**之前**关闭（Windows 不允许重命名仍被打开的文件），临时目录清理必须忽略错误，否则清理失败的异常会吞掉填充率守卫的真实报错。
- 只补一列时不要重跑完整构建：完整构建会用新一版标签文件覆盖线上角色标签。补列走增量补丁脚本，只 UPDATE 目标列，幂等且不触碰标签表。

## 2. 从 infobox 解析的字段（铁律）

- dump 的角色记录**没有中文名与性别字段**，两者只能从 `infobox` 取。infobox 是 wiki 模板原文，**键前带一个 `|` 前缀**，解析必须先去前缀再匹配；对键做全等比较会永不命中，导致字段全库为空且无人发现。
- 抽取逻辑集中在构建脚本的几个解析函数里，支持多值块（逐行 `[值]` / `[类型|值]`，取竖线后的值、丢弃空条目）与内链清洗。性别归一到 `male` / `female` / `?`，与 CEE 反馈判定同一口径。
- **必须保留构建期填充率守卫**：关键字段（中文名、性别、角色标签）任一全表为 0 直接让构建失败。没有守卫时构建会“成功、且没有任何报警”。**必须保留构建脚本自测**，在下载 dump 之前执行以便快速失败。
- 曲目歌手必须在构建期从音乐条目自身的 infobox 解析，同时覆盖单值与多值块（只读单值会整条漏掉多艺人）。该列**没有别的来源**，落成空值会让曲目匹配的歌手加减分整条失效，原版优先退化成只看曲名。
- **改数据列时必须回头检查读取它的每一处。**

## 3. 角色标签

- 原版客户端的标签数据文件是**唯一**可得的标签来源（原版服务端只写不读）。它每周更新，所以**不要把快照提交进本仓库**。
- 日常更新只应用相对上一版的增量 diff，应用是幂等的，已应用版本的指纹记在服务器本地状态里作为下一轮基线。**位点对不上必须退回全量下载并重建**，不能拿旧 diff 硬套（会静默漏掉中间变更）。权威来源地址与默认分支属于部署外部依赖，放本地笔记，以构建脚本参数为准。
- 标签文件的对象字面量用**裸数字键**，不是合法 JSON，解析必须按行补引号；每行一个条目，行首匹配不会误伤标签文本。
- 标签是**平铺集合**（发色与性格混在一起），CEE 的角色标签交集用的就是它；上游的分类只服务编辑与筛选 UI，不参与判定。

## 4. 声优

- 声优关系取自人物-角色关联文件，**必须按作品类型过滤**（只保留动画与游戏），与原版一致；**不得按关系 `type` 过滤**（非零 type 全是配音关系，过滤会误删）。
- 判定用人物**原名**，不用 infobox 中文名：原版取的就是 API 的原名，且同时进元标签与声优列表；用中文名会对不上原版反馈。中文名仅供 UI 展示。

## 5. 登场作品：运行时算，不落库（铁律）

登场作品集由 `CEECharacterRepository` 用联表查询现算，**不得物化**任何登场作品派生表：它既是“角色-作品关系 × 作品”的函数，又依赖房间设置，且算标签权重所需的关系类型也不在物化表里。规则逐条对齐原版：

- 只收主角与配角关系。
- 先按房间设置的大类过滤，为空则回退全部类型（回退保证只选书籍/三次元的房间也能玩，此时音乐类也会被算进来，所以作品表必须含全部类型）。
- 丢弃年份无效与未上映的作品，且**这一步在标签累积之前**，这类作品连标签都不贡献。
- 累积顺序按作品 id 升序（标签权重有“先算元标签、再算普通标签”的累积依赖）；输出顺序才按评分人数降序。
- **剔除 NSFW 是本项目的合规约束**（原版没有）：构建期 NSFW 作品不进角色库（关联一并丢弃，计数非零会让构建失败），运行期抽样与登场作品查询也各自带过滤。**只剔角色库**，歌曲库保留全集的动画元数据。
- 已知差异：dump 没有 `locked` 字段，无法还原原版对它的丢弃。联表会丢掉少量指向不存在作品的行（dump 内部不一致），原版不会遇到。

## 6. 热度与标签池

- 出题是两级采样：先按大类、年份区间、元标签抽作品，再从作品角色里抽一个。dump 没有热度字段，用收藏分布各桶求和近似，与歌库同一口径。
- **标签池禁止落库**：标签池是登场作品的函数，而登场作品依赖房间设置，同一个角色在不同设置下标签池不同。构建只物化**输入**（作品原始标签、元标签、角色-作品关系、角色标签、声优），累积由运行时 `CEECharacterDerivation` 计算后交给领域反馈判定。物化任何一份标签池都等于把某种房间设置写死。
- 不要再引入任何“派生结果”列或表；不要给主键已覆盖的列加重复索引。体积与行数以构建输出为准，不作为固定验收阈值，体积增长时先检查是否引入了派生列或重复索引。

## 7. CEE 运行时资料与补全

- 角色检索的 FTS 为 trigram，**查询串短于 3 个字符必然返回 0 条**，所以短查询必须回退参数化 `LIKE`（转义通配符）；较长文本使用带引号的 FTS 短语。`LIKE` 不区分大小写且会命中别名串里的英文片段，需要配合排序与截断。别名与 API 补充后的名字参与检索；作品检索覆盖书籍、动画、游戏、三次元，不复用仅动画的歌曲查询。
- `CEECharacterWorkerProvider` 是生产查询入口，同步 SQLite 查询只在独立 Worker 内执行。在途请求与返回条数有上限；读取比硬上限多一条用于检测超限，**超限明确失败，不静默截断规则**。
- 随机出题先按年份、大类、元标签与热度选作品，再按作品关系顺序选角色；无候选、缺角色、未导入目录分别返回业务错误，**不把设置替换成另一套筛选范围**。目录模式只读已导入的成员快照。
- 原版支持外部标签的作品登记在唯一列表里，构建器与运行时共用。外部标签表只保存原始作品、角色、分区与标签键的有序关系，不保存 HTML 或房间派生状态；文件缺失、分组损坏或全库空标签必须令构建失败；空键表示原版未录入，不作为线索导入。
- 可见作品列表决定作品数量、评分与年份；比较用作品列表额外保留登记游戏的主配角关系，**仅用于共同作品判定**，不得塞进可见列表（会让跨类型作品计数与评分变化）。外部标签按判定数组中首个登记作品取值，沿用同分区同标签键命中规则，无数据为空，不跳到第二个作品；不参与普通标签 BP；仅下发猜测标签及命中结果，不泄漏答案完整标签。
- 图片补全复用回填缓存格式（规则见 [BangumiApi](BangumiApi.md#2-api-回填缓存)）。补全队列有界并发、相同角色请求合并；429 冷却，只有有效响应确实无图或角色 404 才进短时负缓存。网络、限流、服务端失败与无效响应必须返回明确业务错误且可重试；**不得用图片降级捕获本地 JSON 损坏或 SQLite 持久化失败**。
- 同次角色响应的有效字段（名字、中文名、别名、简介、有效性别、收藏与评论数之和）存入补全表，**不以缺失或空字段覆盖已有资料**。这些字段只在后续读取时覆盖基础库；已返回的角色对象不被异步修改。每局角色资料由游戏服务冻结，不能因头像加载完成改变本局答案、历史猜测或分数。API 不替代本地作品、角色关系、标签或声优。
- 目录仅在用户执行导入时读取，分页读取有单页与总量上限；收齐并校验全部分页后原子保存。缺失或受限作品返回 `missingSubjectIds`，不为它们联网补抓；分页失败保留之前完整导入结果，**禁止保存部分目录**；抽题路径绝不请求目录 API。
- 关闭前排空资料请求及持久化任务，再关闭 SQLite；测试使用隔离临时库与注入的网络响应和时钟，普通测试及真实本地库小查询不得访问上游。
