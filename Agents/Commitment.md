# 提交、版本与玩家更新日志

每次提交查阅前两节；只有维护产品版本或 `changelog.json` 时才需要阅读后续章节。

## 原子提交

- 每完成一个独立修改点，通过对应验证后立即提交；不积攒到任务结束再拆分补提。
- 协议与两端消费点等不可分割的配套改动放同一提交，无关改动分开。
- 提交前检查暂存区，只纳入本任务内容，不包含用户已有改动、私密配置、临时文件或无关生成物。
- 验证范围见 [Testing](Testing.md#验证范围)。本地提交与推送、部署是不同动作，后两者按用户授权执行。

## 提交信息

格式：`type(scope): 中文摘要`。摘要与正文均以中文写作，不写英文描述；专有名词（如 R2、LFS、AMLL）可保留英文原文，但不得通篇英文。英文仅限固定的 type、scope 字段与专有名词。摘要最多 20 字（含标点；专有名词的英文字母逐字计入）。

| 字段 | 允许值 |
|---|---|
| `type` | `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert` |
| `scope` | `Faker`（谁是卧底）、`Song`（猜歌）、`CCB`（猜角色）、`Core`（公共能力、工具链、文档） |
| 摘要 | 一个原子动作，例如 `docs(Core): 精简文档导航`、`fix(Faker): 修复提前结算` |

scope 区分大小写，不使用 `server`、`client`、`shared` 等自建作用域。提交前校验标题：

```regex
^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)\((Faker|Song|CCB|Core)\): (?=.*[\u4e00-\u9fa5])[\u4e00-\u9fa5\dA-Za-z，。、、“”《》（）]{1,20}$
```

该正则要求摘要至少含一个中文字符（不接受通篇英文），允许数字、专有名词英文字母及列出的中文标点，长度上限 20 字（中英文逐字符计入）。正文仍须人工确认中文与准确性。

- **摘要须自然可读**：不允许为了卡字数上限把摘要写得晦涩难懂——删减关键信息、生造缩写、牺牲语义连贯都不可取。接近上限时先精简冗余词；确实无法在限内清晰表达时，用正文展开细节，或在改动确可拆分时拆成多个原子提交。
- **正文可详细展开**：正文（description）可以写详细的改动内容（动机、范围与验证），但依旧只能使用中文，专有名词除外。
- **禁止工具与模型署名**：提交信息（标题、正文及尾部注记）不允许添加任何 Agent 工具或模型署名，如 `Co-Authored-By: <模型>`、`Generated with <工具>`、机器人图标或其他生成来源标记；署名只保留真实贡献者。

## 产品版本

用户可见版本遵循 SemVer 2.0，展示为 `V<major>.<minor>.<patch>`。真相源为 [changelog.json](../Client/src/data/changelog.json) 中的最大版本；包清单 `version` 只满足 npm/Bun 格式要求，不作为产品版本。

| 变化 | 递增 |
|---|---|
| 不兼容的重大变化 | major |
| 大型新功能 | minor |
| 一轮缺陷修复 | patch |

## 日志结算窗口

每次编辑 `changelog.json` 都结算上次编辑以来的全部用户可见变化：

1. 用 `git log -1 -- Client/src/data/changelog.json` 找到上次结算提交，检查其后至当前 HEAD 的全部提交，并纳入本次待提交的用户可见改动。
2. 同类变化合并概括，不能只登记触发编辑的最后一条。只有内部重构、测试、CI、文档、部署方式或遥测变化时，不新增版本，也不编造玩家文案。
3. 有用户可见变化时按版本表递增，将新条目放在 `entries` 前部。纯文档任务无需打开新的结算窗口。

## 日志结构与文案

```json
{
  "entries": [{
    "version": "1.2.3",
    "date": "YYYY-MM-DD",
    "content": { "feat": ["新增发送表情包功能"], "fix": ["修复已知问题"] }
  }]
}
```

- `content` 按 `feat`、`fix`、`chore`、`perf`、`style`、`refactor`、`docs` 等类型聚合；无更新的类型省略，不用空数组或空串占位。
- 分类优先用 `string[]`；单条微小更新允许字符串。由 [Changelog.ts](../Client/src/lib/Changelog.ts) 解析纯文本及轻量行内标记：行首 `-`、`**加粗**`、反引号、`[文字](链接)`。不写 HTML，不用 `dangerouslySetInnerHTML`。
- 文案面向玩家，平实、简短，优先用“新增 / 修复 / 优化 / 完善”等动宾短语。单条 6—25 字，建议每版 2—4 条、每类 1—2 条。
- 不列函数、变量、依赖库或内部实现；同类细节合并成一条。不加营销语或“提升……体验”“显著减少……”等收益性尾句，避免“并 / 且 / 从而”连接。
- 简短条目末尾不加句号；必要的复合条目用中文逗号。可用“优化字体表现”“完善全栈异常捕获与监控体系”，不要附带工程汇报。
- 日志从源码导入并随构建发布，不放到 `public/` 的固定 URL。构建期数据也应进入有内容哈希的产物；贴纸清单通过 `virtual:sticker-manifest` 动态导入，不能复制到无哈希公共文件。
