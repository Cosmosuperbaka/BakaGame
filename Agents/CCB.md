## 产品边界

- 房间来源分为增强房与原版房。增强房由本服务权威执行；原版房实际建在配置的原版服务器，
  每位增强版玩家通过独立上游连接参加。原版适配器不另外运行本地比赛。
- 两类房的增强版角色检索与判定资料均来自 SQLite。原版客户端资料版本不同，允许反馈差异；
  兼容房最终状态、计时、积分服从远端。上游当局答案快照必须保留，不擅自换成本地答案。
- 三个小游戏暂时使用公共默认头像，不实现角色头像选择、抽卡、兑换或 QQ 登录。
  增强版无角色头像本命奖励，首猜奖励保留；原版玩家已有本命机制保留。
- 增强版删除玩家短留言，由聊天替代。兼容房新增聊天只在增强版玩家之间互通，
  不把原版短留言伪装成聊天，也不改原版客户端的留言功能。聊天栏第一行固定提示「聊天仅增强版玩家可见」。
- 增强版的**主页入口在生产部署临时下线**（2026-10 起，仅主页入口）：生产构建把它渲染成
  「即将上线」的不可用卡片，开发环境保留可进入的入口；`/ccb` 大厅与 `/ccb/room/<房号>`
  直链照常可用，服务端不做拦截。开关是 [LandingPage.tsx](../Client/src/pages/LandingPage.tsx)
  的 `isCcbHomeEntryAvailable`，恢复上线时改回 `true`。

### 统一房号

- 大厅、路由（`/ccb/room/<房号>`）与会话只认一个 4 位房号，增强房与原版房共用同一号段，互不占号，
  唯一持有者是 `CCBRoomDirectory`。增强房的房号即自身 id；本站在原版服务器建房时直接用 4 位号作上游房号；
  原版客户端建的 UUID 房由服务端分配别名：按上游 id 散列取初值、线性探测避让，
  刷新之间与服务重启后同一批房间尽量得到同一个别名。上游真实房号不下发给客户端。
- 别名只在一次成功的上游列表里该房间已消失、且没有本地会话（含建房确认途中）时释放；
  上游暂时不可达不影响现有别名。入房时房号未命中会回源刷新一次（与大厅共用 5 秒缓存节流），
  重启后的首个分享链接也能解析；仍未命中返回 `ROOM_NOT_FOUND`。
- 大厅合并两类房间：增强房在前，原版公开房按上游顺序在后并带「原版」徽章。原版列表不提供旁观人数，
  `spectatorCount` 为 `null`，界面不显示该数字，不伪造为 0。
- 私密与其它游戏同口径：增强房私密即有密码，带锁进大厅；切到私密时必须给新密码或已有密码，留空保留原密码，
  转为公开清除密码。缺密码回 `PASSWORD_REQUIRED`，错密码回 `PASSWORD_INCORRECT`。同一连接对同一房间每 60 秒
  最多尝试 5 次，**在校验之前计数**，超限后正确密码同样回 `TOO_MANY_ATTEMPTS`。原版没有密码机制，
  其开关只控制是否出现在大厅，非公开原版房凭别名链接仍可进入。界面上这个开关叫「不在大厅显示」（开启即
  `visibility: 'private'`）并常驻上述说明，建房弹窗（`CreateRoomDialog privacy="unlisted"`）与等待页设置同一措辞；
  建房时就可选择不进大厅，服务端建好房后与房间设置走同一条 `toggleRoomVisibility`。增强房的开关叫「私密房间」。
- 上游地址及 AES 配置仅在服务端环境变量；绝不写入前端构建或日志。

## 玩法与状态

`waiting → preparing / answering → guessing → settled → waiting`。
局号与同步轮号是不同字段。开局冻结设置；猜测只提交角色 ID，不接受客户端判中结果。
支持普通、同步、血战、角色全局 BP、标签全局 BP 的全部组合，个人、1—8 队、观战，
随机与手动出题、目录与追加作品、文本与图片提示。

- 普通首位猜中结算；同步等当轮参与者全部完成才判定；血战继续到全部参与者结束。
- 队伍共用尝试记录、次数与行动计时；超时按当时在线且可行动的队员人数扣次数。
- 同步血战同轮答对并列，基础分在同步轮开始时冻结；两个第一名之后下一位第三名。
  非同步血战按消息顺序。原版同时修复这一规则。
- 增强房血战出题奖励的分母冻结为开局实际猜题人数，排除出题人及其观战队友；
  猜题者后续断线、清理或离开不缩小分母。此处纠正原版按结算时在线人数重算、
  且误计出题人观战队友而导致奖励波动的问题。
- 同步胜者按自己的首猜、本命与快速猜中奖励结算，不共享首位胜者奖励；原版同时修复。
- 基础胜利分 2；首猜额外 12；非首猜第 2—3 次额外 2，第 4 次至次数上限一半向上取整额外 1。
  血战基础分按开局可猜人数减此前胜者数、最低 1。作品分与出题人奖惩保留原版口径。
- 同队共享次数，但胜者、贡献者与奖励用明确记录，不从共享表情串反推玩家身份。
- 出题人与其队伍本局观战；中途新成员本局观战；已结束玩家只能观看、不能重复提交。
- 手动指定出题人的权限独立于随机开局准备检查。服务端通过 `setterCandidateIds` 下发候选名单，
  客户端只消费名单；增强房候选必须在线，且排除出题人与队友后仍有可猜者。原版名单遵循上游权限。
- 角色 BP 保留本人重复、同步同轮及正确答案例外；被拒绝猜测不扣次、不登记标签。
  本人重复豁免不能扩大到同队成员；队伍共享次数不等于共享重复豁免。
  作品分从全局有序的 `round.guesses` 比较队员首次作品命中位置，不比较个人数组索引、姓名或同毫秒时间戳。
  先选队内最早命中者，再排除本人实际猜中角色的情况（不转赠次早者）；队友最终猜中不能抹掉原贡献者的作品分。
- 标签发现与有效猜测原子提交，私有视图裁剪隐藏标签。同步轮末处理沿用原版口径。
  原版服务部署 `2778144` 后通过 `playerGuess.sharedMetaTags` 同步登记，并以
  `tagBanApplied` 确认；旧原版部署仅能退回独立标签事件，最后同步提交者的标签可能延至下一轮。
- 默认多人设置为近五年、热度前二十、十次、每次六十秒、作品和角色各四标签。
  预设基础值不同，不能替代多人默认值。不限行动计时仍有房间闲置与阻塞阶段超时。

## 数据和隐私

- 只读基础库与可写补全库组成统一查询结果；API 补全的头像原始 URL 与有效角色资料持久化，
  周更不覆盖补全库。禁止把网络查询作为 SQLite 角色检索失败后的隐式回退。
- 目录成员先同步入库，对局只用已落库成员；缺失条目给出明确数量。
- 登场作品和标签池按房间设置运行时推导；具体字段口径见 [BangumiApi](BangumiApi.md#本地数据集构建)。
- 原版登记游戏的额外作品关系单独参与作品命中，不改变可见作品数量、评分及年份。
  外部标签保留分区及同键命中高亮，使用服务端 SQLite 原始资料，不透传上游 HTML；
  外部标签不参与普通标签 BP，答案的完整外部标签继续受私有状态边界约束。
- 答案、设置和已使用角色视图在局内冻结；后台资料更新不得改变已给出的线索。
- 兼容房由房间统一维护递增对局代数，不能单凭答案载荷哈希充当局号。同载荷在结束后
  再次开局也必须重建资料与自动提示缓存；多条上游连接只绑定同一代数，旧连接不得
  回退共享缓存。猜测、图片、附加标签及确认响应在异步返回后复核代数。
  仅当前代数的结束事件关闭共享局；已知旧载荷的迟到开局事件不回退房间，
  最近 256 个载荷指纹使用有界缓存登记。上游不提供局 ID：未观察到结束边界且载荷
  完全相同的开局事件只能按同局重发处理，不能声称协议可以消除这种不可判别情况。
  同房同局共享本地角色查询与附加标签资料，连续下一局重新读取。
  后来者进房即沿用共享房间已知代数，不等下一次开局。两种来源的局号都在进入猜测时递增，
  顶栏在准备与出题阶段显示即将开始的下一局（`ccbDisplayRound`）。
  旧原版答案仅在关联登记游戏时从 SQLite 补充附加标签和缺失作品名称，禁止覆盖上游
  答案数值、作品编号或可见作品统计；本地角色不存在表示无附加标签，数据库故障须报错。
  普通角色不为可选标签额外读库；异步猜测跨过上游超时或同步换轮后必须拒绝旧动作。
- 自动文本提示服务端生成一次；图片提示由服务端生成当前允许的模糊版本，
  未解锁时不得发送原图、原图 URL 或可猜出的资源路径。提示请求必须鉴权。
- 文本与图片提示阈值零表示关闭。被隐藏标签同时移除原文与命中标志。
- 数值比较符号表示「猜测值减答案值」，界面箭头表示答案方向：正号向下、负号向上；
  未知评分和年份显示「未知」，不能显示内部哨兵值。
- 公开快照只含公开房态。本人/队伍猜测、观众/出题人答案分别进入私有状态；
  兼容适配同样按连接视角裁剪，不能合并所有上游玩家的私有事件。
- 原版客户端可解密答案是其协议局限，兼容房不宣称全房答案保密。

## 工程与验收

- `/api/ccb/ws` 使用平台信封、TypeBox 严格边界、会话幂等与 RFC 6902 状态同步。
  领域、数据访问、原版适配和视图各自独立；前端复用 common/ui，不横向导入别的游戏组件。

### 解析与错误应答

- **可选字段必须同时接纳「缺席」与「显式 `null`」**（`t.Optional(t.Union([..., t.Null()]))`）。
  `t.Optional()` 只容忍字段缺席，而前端把「尚未加入房间」表示为 `null`，`JSON.stringify`
  会原样保留 `null`：只写 `t.Optional` 会让这类合法请求在**解析阶段**就被判 `INVALID_MESSAGE`，
  表现为 400 + 微秒级耗时 + 日志 action 仍是 `WS raw`（`parsedType` 未被覆盖是本类故障的判定特征）。
  放开 `null` 只影响「未提供」语义，不得放松任何取值约束（类型、长度、枚举仍须锁死）。
- **解析失败必须保留信封身份，错误包 `id` 绝不允许退化成占位值**。
  解析抛错时 `parsedId` 还是初值，客户端 `pendingRequests` 匹配不到该 id 就**静默丢弃**错误，
  而进入房间类命令用 `timeout: 0` 永不超时——页面只表现为一直卡住、前端毫无提示。
  网关须从校验失败的原始载荷里抢救 `id`/`type`（仅供错误回包与日志，不参与业务执行），
  并把裁剪后的载荷形态（键名、键数、截断样本）写进告警日志，让「只看到 `WS raw`」不再发生。
- **可恢复状态不得交给 schema 拒绝**。恢复会话的凭据为空或缺席属于「会话失效」而非
  「消息非法」：若按 `minLength: 1` 在解析层拦下，同样落进上面的静默陷阱。
  此类字段放开为空/缺席，由业务层回 `SESSION_EXPIRED` 这类可归因、可提示的错误码。
- 客户端只见到统一房号；服务端内部的 `original:` 连接标记从不下发，信封 `roomId` 与其它游戏同为 32 字符上限。
  `ccb.room.join` / `ccb.room.reconnect` 不带来源字段，只有 `ccb.room.create` 声明要建在哪个服务器。

### 入房与会话恢复

- **进入房间期间客户端不得抢跑状态同步**。服务端 `enter()` 在返回结果**之前**就 `publish()`
  新房间状态，快照事件因而先于进入房间的 ACK 到达；此时客户端尚无凭据，
  抢发的 `requestSync` 会被原版会话校验判 `SESSION_INVALID`，进而作为永久错误清掉
  刚建立的会话——直接表现为「加入原版房间失败」。客户端应把该请求压成欠账、
  待 ACK 写回凭据后再补发（补发时必须先取走欠账标志，`resetCCBStateSync` 会清掉它）。
- 客户端会话凭据只按统一房号存储；来源与上游配置由服务端会话表判定，凭据对不上时回
  `SESSION_NOT_FOUND` / `SESSION_EXPIRED`，客户端据此删除。确认加入后授予聊天身份，被踢/退房即时撤销。
  上游无法确认同号房是否重建时清除旧聊天，禁止无限重试 join 导致意外建房。
- 页面生命周期是唯一的房间恢复入口，连接监听仅订阅大厅；断线清除旧视图，卸载释放连接、
  重试定时器和待请求，保留可恢复的标签页凭据。原版过期凭据须删除后允许重新加入。
- 出题、续局、目录导入及图片处理等耗时命令依赖服务端受控截止时间，客户端不另设短超时报假失败。
- 来源切换、会话恢复和主动请求同步都重置公开与私有状态的差量基线，首次发送完整状态。
  重连宽限内保留的上游会话计入玩家数，但没有下游连接时不得计入在线人数。
- 原版 `/api/list-rooms` 返回含非公开房的完整列表：它同时用于入房前的存在性检查与统一房号目录的别名分配，
  大厅只展示其中的公开房。
  提示阈值为零表示关闭，保留数组位置，不得压缩后与提示文本错配；作品搜索关闭时，
  服务端拒绝当前猜题者的作品与作品角色查询，观战者和已结束玩家可查看。
- 原版房名的状态确认按上游三十字截断规则，不能用更短的本地长度等待永远不会出现的确认。
  玩家身份比对亦须宽容：上游玩家编号可能是数字、用户名可能带首尾空白，
  身份解析要显式归一化（数字转字符串、按 `trim()` 比较），
  否则「加入确认」谓词永不命中，加入只能等到 8 秒超时才失败。

### 生命周期与并发

- 房主重连 60 秒、空房宽限 90 秒、离线清理 3 分钟、闲置清理 10 分钟；
  房间定时由服务端驱动，断线不能导致同步永久卡住。
  唯一猜题人暂时离线不能直接结算；保留未结束席位供刷新恢复，离线清理、明确退出或放弃才结束该席位。
- 异步出题任务使用独立操作标识，截止时间不能兼作身份。猜测查询回来须复核局、
  同步轮和次数；同角色并发返回时复用首次接受的冻结资料。入房密码校验回来须确认连接仍登记。
- 原版随机开局与手动答案准备各持独立操作标识，冻结设置及原连接、房间代数、共享局、阶段、房主和出题人。
  每次角色或图片查询 `await` 后、发出上游事务前，复核该操作仍归当前连接且仍有对应权限与准备条件；
  命令串行队列不串行上游广播，也不能替代归属复核。断连、连接替换、离房、房主/出题权变更、取消出题、
  设置变更或新局撤销旧准备；权限随后恢复仍不能复活旧任务。离房即时撤销，不排队等待资料查询。
  失败仅回滚仍由该任务拥有的准备阶段，不能覆盖上游新局或新出题人；已经发出的事务仍服从上游确认。

### 搜索索引与 Bangumi API 口径

- CCB 的角色和作品搜索使用服务端配置的 `CCB_MEILISEARCH_URL` 对应的 Meilisearch，
  客户端统一通过 `meilisearch` JavaScript SDK 访问。SQLite 只保存详情和关系，
  不再作为生产搜索排序器；Meilisearch 返回的命中顺序必须原样用于详情回填。
- 索引排序规则与 Bangumi server 的 `internal/search` 一致：先按
  `exactness → words → typo → proximity → attribute → sort`，角色随后按
  `id:asc → comment:desc → collect:desc → nsfw:asc`，作品随后按
  `id:asc → rank:asc → score:desc → nsfw:asc`。角色的 `name`/`aliases`、作品的
  `name`/`aliases` 是唯一搜索字段；类型、标签、元标签、日期、评分、评分人数、排名和
  `nsfw` 只作为过滤或排序字段。
- Worker 初始化会校验服务健康状态、创建/校正两个索引的字段设置，并在文档数量不一致时
  从本地 SQLite 按批次重建。未配置 URL 的测试夹具保持显式本地模式；生产配置必须提供
  可用的 Meilisearch，不能在运行期静默切换到另一套排序逻辑。
- 搜索回归以 Bangumi API 的过滤表达式和固定语料为参照，命中 ID 集合及顺序相似度必须达到
  99.9%，精确名称、别名、类型和 NSFW 边界样例要求完全一致。

### 验收范围

按改动命中相关场景，完整重构或发布验收覆盖下列矩阵；验证命令见 [Testing](Testing.md)。

- 核心验收：四开关 16 组合、个人/组队、自动/手动、并发和末次猜中、超时、重连、
  观战隐私、连续两局、混合客户端互通、三档响应式、生产资源与容量。
- 玩家栏与另外两个游戏共用 `components/common/PlayerRow.tsx` 与首字方块头像。
  身份、姓名、状态、分数与房主操作都由该行承载，CCB 只注入次行内容（队伍与次数）
  与第三行的猜测进度；聊天保留独立区域，手机及平板都有入口。
- 状态徽章与另外两个游戏同口径：旁观分组不重复「旁观」，等待阶段表达准备状态；开局后
  两种来源都把出题人记为观战，客户端按 `setterPlayerId` 标「出题」。游戏区的次数行同理，
  出题人、其队友与中途加入者看到身份说明，不显示对他们无意义的猜测次数。
- 旁观切换只在等待阶段出现，两种来源开局后都不接受改身份。房间关闭观战后不再提供「加入旁观」，
  但已在旁观的人仍能「取消旁观」回到玩家组；「我的队伍」只给玩家组成员。
- 猜测进度取服务端 `marks` 字符串渲染：原版房直接沿用上游原样，客户端不改协议，
  只在渲染层把标记翻成图标（猜中、作品命中、超时、次数用尽、放弃等），
  整串作为一个图像读给读屏，悬停提示给出同一份文字描述，不靠颜色传达。
