# 协作与决策透明

需求跳过目标直接给方案、改动涉及架构／状态管理／数据模型／权限／依赖／路由／主要 UI 结构、或需要在多个做法之间取舍时查阅本文。本文只写协作方法与决策口径；代码层约束见 [Spec](Spec.md)，验证范围见 [Testing](Testing.md)，授权与交付边界见根 `AGENTS.md`「完成与决策边界」。

| 工作范围 | 章节 |
|---|---|
| 需求只给了方案没给目标 | §1 |
| 改动跨模块、动到契约或主要布局 | §2 |
| 文档与实现不一致、本次要改哪份文档 | §3 |
| 交付说明与更优方案的提出方式 | §4 |

## 1. 先对齐目标，再谈方案

- **按缺口触发**：只有当产品目标、使用场景或成功标准的缺失会改变实现方向时，才先问再动手，并一次把缺口问清。范围明确、能一句话说清验收的改动直接做，不为「确认」增加往返。
- 提问与回复先拆四层：**用户目标 → 当前方案 → 可选方案 → 推荐方案**。用户给的是方案而不是需求时，先复述理解到的目标与成功标准，再判断该方案是否达成它——不默认方案即需求。
- 目标问题问方向与验收（给谁用、什么算做好），不问实现细节；实现细节自己从代码与文档取证。
- 可验证结果：一轮补齐缺口后即可开工，交付后不出现「目标理解错」导致的整块返工。

## 2. 动手前的决策透明

- 命中开头列举的任一改动领域时，动手前用两三行说明：**判断依据**（为什么这个做法成立、否决了什么）、**影响范围**（涉及哪些模块与文件）、**可能被破坏的契约**（协议与字段、存储键、调用方、文档）、**验证方式**（按 [Testing](Testing.md#验证范围) 选定的检查范围）。
- 存在多条可行路径时给至少两个方案，按**复杂度、扩展性、风险、开发成本**比较后推荐一个。只有一条合理路径时直接说明无替代方案，**不编造对比凑数**。
- 局部 bug 修复、文案修订、补测试不触发本节，避免把小任务包装成大决策。
- 不为了短期跑通引入长期难维护的临时方案；必须临时处理时按 [Spec §1](Spec.md#1-优先使用原生标准与成熟生态) 留标记，并在交付时点名，不作为交付终点。
- 可验证结果：读者能在交付说明里找到「为什么这样做」，而不只看到「改了什么」。

## 3. 文档与实现一致性

- 本项目规范分散在根 `Agents/`、`Server/docs/`、`Client/docs/`，**没有根 `/docs` 目录**。先用根 `AGENTS.md`「按任务查阅」定位权威文档，同一事实只在唯一维护位置改一次，不复制到多处。
- 涉及功能、信息架构、数据结构、权限模型或主要布局的调整时，动手前点名本次会改到哪份文档并给出更新大纲（改哪节、为什么改），与代码改动落在**同一批**提交。写法与文档红线见 [Spec §3](Spec.md#规范维护)。
- 实现与文档方案发生偏离时，交付说明必须写清三点：**偏离点、偏离原因、潜在影响**。缺任何一点视为未说明。
- 发现文档与实际不一致，在同一批改动里三选一处理：改代码回到规范、改文档承认现状、或把暂不处理的偏差与理由写进 `.agent-notes/`。不留无人认领的漂移，也不留只有聊天记录的口头规范。
- 一致性核对只在本次命中的文档与改动范围内进行；全仓体检走 [project-quality-audit](../.Skill/project-quality-audit/SKILL.md)，普通开发不主动扩大。

## 4. 讲清判断，也提出更优解

- 交付时把关键工程判断讲出来（为什么选它、放弃了什么、留下什么限制），压缩到几句，不为此另写长篇文档。解释的目标是让人理解做法，而不是罗列步骤。
- 当存在明显更好的长期方案而当前指令只要更短的路径时，**先提出该方案与代价，再按用户选择执行**：不沉默照做，也不擅自把用户的方案换成自己认为更好的。
- 用户已经给出的技术决定不反复复议；只在发现真实风险（数据丢失、死锁、安全面失效、契约破坏）时第二次提出，并说明触发风险的具体条件。
