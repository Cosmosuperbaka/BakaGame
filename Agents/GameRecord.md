# 对局记录

涉及对局记录的写入、保留、字段口径或按记录做统计时查阅。表结构与连接见 [Database](Database.md)。

## 1. 边界

- 一局 = 一个房间从创建到销毁；局内每次结算 = 一个回合。记录按「一局 + 若干回合」保存，回合序号从 1 开始。
- 记录只服务后台复盘与统计，不承担实时回放；房间实时状态仍为纯内存，记录不反向影响对局。
- 三款游戏地位相同，都在「一次结算」时经端口 `GameRecorder`（`domain/GameRecord.ts`）交一个回合，房间销毁时再调 `finishRoom` 收尾；服务以可选依赖注入，未配置数据库时不注入，即不落库。
- 猜猜呗只记录增强房：原版房的对局在上游服务器进行，本端拿不到完整答案与全员猜测。

## 2. 写入点

| 游戏 | 回合时机 | 摘要 `summary` | 时间线 `timeline` |
|---|---|---|---|
| 谁是卧底 | `finishRound`（含主动中止，`winner=aborted`） | 胜负、原因、词对、出题人、全员身份、天数 | 发言、投票、夜晚行动、白板猜词、离场，按时间合并 |
| 猜歌/猜番 | `finishRound`（含房主跳过，`skipped=true`） | 题型、答案歌曲/番剧、出题人、猜中者 | 逐次猜测与结果 |
| 猜猜呗 | `CEERooms.publish` 发现进入 `settled` | 答案角色、出题人、名次、模式 | 逐次猜测与命中 |

- 房间销毁统一经各服务的 `closeRoom` 调 `finishRoom`：`WhoIsFakerService`、`SonGuessrService` 与 `CEERooms` 三处；结束时刻推进到销毁时刻。
- 猜猜呗的结算散落在多条领域路径，但都以一次发布收尾；按结算摘要对象去重，结算后的多次发布只记一个回合。
- 玩家行分两层：`game_record_player` 是本局累计总分（按 `playerId` 合并各回合增量），回合行里的 `players` 保留该回合的得分增量。`userId` 取连接上的登录身份，游客为空；昵称截到 64 字符。
- 摘要只放复盘需要的最小信息，不放歌词、音频地址、cookie、头像等大字段或敏感字段。

## 3. 落库与保留

- 两张表：「一局」在 `game_record`（游戏、房间号、回合数、创建/结束时刻、去重玩家数），「回合」在 `game_record_round`（回合序号、起止时刻、得分增量、摘要、时间线），外键级联删除；见 [Database](Database.md#3-schema-与迁移)。
- `GameRecordService` 按房间会话聚合并串行写入（同一局的回合按结算顺序落库，聚合行不会被旧快照覆盖），失败只记告警，绝不抛回游戏服务。数据库不可用时最多积压 1000 个待写回合，超出丢弃并告警。
- 单个回合的时间线序列化上限 64 KB：超出保留前段并追加 `{ type: "truncated", omitted }`；后台详情的全房合并时间线出口上限 1 MB。
- **永久保留**：不按时间清理。2026-10-18 之前的 7 天滚动记录已随 `0003_game_record_room_sessions.sql` 清空。
- 未走销毁流程（如进程重启）时房间状态随内存消失，记录停在最后一个回合的结束时刻，仍是一条完整的一局。
- 按日统计以北京时间切日：`ended_at`（UTC）加 8 小时后取日期，与访问统计同口径；「对局」按房间行计数，「参与人次」按每局去重玩家数累加。

## 4. 验收要点

命令与验证范围见 [Testing](Testing.md#验证范围)。

- 记录服务：同房多回合聚合成一局、玩家分数累计、写入失败隔离、64 KB 截断、重复回合与销毁后迟到回合被忽略、空房间不落库。
- 三款游戏结算各交一个回合；谁是卧底关房触发 `finishRoom`。
- 对真实 TiDB 的验证（迁移、事务写入、按账号查询、按日聚合）属于一次性人工验收，结束后删除测试数据。
