# 开源致谢与版本信息页

维护 `/credits`（开源致谢 / 更新日志 / 提交历史）、参与开发的大模型名单、品牌图标或依赖许可证数据时查阅本文。页面布局与交互规范见 [DesignGuide §7.5](DesignGuide.md#75-版本信息与开源致谢页)，更新日志文案与版本结算见 [Commitment](../../Agents/Commitment.md)。文件位置、数据结构、命令读代码，本文只留约束。

## 1. 数据来源原则

- 更新日志、提交历史、依赖清单、许可证原文都由构建期从**真相源**生成，不手写、不在文档或页面里写死依赖数量、包名列表或版本。新增依赖不需要手工登记。
- 手写维护的只有两份：参与开发的大模型（`CONTRIBUTING_MODELS`）与核心技术栈（`CORE_TECH_STACK` 及分类），都在 `Client/src/data/CreditsContent.ts`。
- 许可证原文不常驻页面，展开某个包的许可证区时按需懒加载；失败不缓存。
- 包链接只放行绝对 http(s)。`repository` 的各种简写写法要归一成仓库页，认不出就给空串，页面据此不渲染“项目主页”。不要把简写原样输出当 `href`，会解析成站内相对路径变成死链。

## 2. 模型署名与品牌标识

`CONTRIBUTING_MODELS` 是“实际参与过本项目开发的大模型”的唯一定义处。

- **只在实际改动后署名。** 提交过代码、数据、文档、样式或配置等仓库文件改动的模型，在完成改动后把自己的名字加入对应公司；仅参与讨论、咨询、评审或规划的不署名。
- **叫不出型号就不登记。** 确认真实型号只认一种证据：自己运行上下文（提示词里的模型标识）里的真实发布名。内部别名、会话日期和自我印象都不算，据此拼出的条目名是错误信息。确定不了时不写条目，只在交付说明里写明改动由哪个会话完成，由维护者按官方发布名补登记。
- **排序。** 公司顺序取数组声明顺序，同一公司的模型按发布日期从早到晚；展示前统一经排序函数收口，数据文件里追加不需要手动插到正确位置。新增公司追加到数组末尾，分组标题写公司或 AI 团队名，不写模型家族名。
- **只写模型名。** 不写分工、日期或宣传语。
- **发布页链接。** 每条尽量带 `url`，优先厂商官方新闻/公告页，其次官方文档的版本说明；深链要落到对应版本那一节，浅链等于链错。确实没有公开页面时省略 `url`，徽章退化为静态标签，不放死链。
- **每条都带 `logo`。** 公司用厂商标识，模型用模型家族标识；是两枚不同的官方字形就分别登记，相同可以复用同一个键。

品牌图标：

- 统一走 `components/credits/CreditsIcons.tsx` 的 `CreditBrandMark`，品牌键为 `CreditBrandId`。
- 来源优先级：simple-icons（逐图标子路径引入，不走聚合入口）→ 已引入的 AI 厂商图标包（以 CSS mask 渲染成单色，不贴彩色位图）→ 才是自备资产放进 `Client/public/assets/brands/`。优先复用已引入的图标包，确实没有才新增自备资产。
- 自备资产的文件末尾用 HTML 注释登记来源 URL、许可证与改法，资产校验测试会核对。来源与许可必须允许再分发。
- 品牌图标只标注依赖、技术栈或模型/厂商本身；指向站外平台的链接图标走 FontAwesome（见 DesignGuide §2）。没有品牌字形的包用通用图标回退，不用近似品牌顶替。npm 别名包与被别名的包共用同一品牌键。
- 新增品牌的最小路径：加品牌键 → 在图标映射里给出来源 → 在数据文件里引用。

## 3. 展示约定

展示规范以 DesignGuide §7.5 为准。这里只补数据侧约束：

- 依赖清单一级只列直接依赖，搜索、筛选、空状态都作用在主包上；子依赖与间接依赖走二级抽屉逐级下钻。
- 核心技术栈卡片的版本按 `packageName` 从依赖清单取；非 npm 运行时或非 Client 依赖不展示版本。

## 4. 验证与维护

- 验证范围按 [Testing](../../Agents/Testing.md) 的矩阵：数据管线改动对应局部客户端逻辑与构建插件，页面改动对应页面样式或动效与 Storybook。
- 浏览器检查覆盖窄/中/宽三档宽度、搜索无结果、License 筛选、抽屉下钻与返回、许可证折叠展开的各状态，以及减弱动效。
- 改动确认的署名、依赖数据或展示约束，同步回本文与 `CreditsContent.ts` 的注释，不只留在聊天或提交信息里。
